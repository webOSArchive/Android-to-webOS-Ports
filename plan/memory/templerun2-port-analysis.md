`templerun2_1.2.1.apk` (in the driver workspace). **Unity 3.5.7f6** game; logic in C# on **Mono**. Two ARMv7 **bionic** native libs only: `assets/libs/armeabi-v7a/libunity.so` (6.8MB) + `libmono.so` (3.8MB). (The `lib/armeabi-v7a/` copies are tiny proxy stubs.) Bionic confirmed: imports `__errno`, `liblog.so`/`__android_log_print`, no GLIBC versioning. Managed DLLs in `assets/bin/Data/Managed/` (Assembly-CSharp.dll etc.); engine data in `assets/bin/Data/` (Unity ver in `mainData` header).

**No direct IPK-patch port possible** — it's a closed Android/Unity/bionic stack, not a webOS-native binary. Needs a compat wrapper (see [[android-apk-port-triage]]).

**Good news from recon — the wrapper is bounded:** libunity exports `ANativeActivity_onCreate` and imports the NDK C API (`ANativeWindow_*`, `AInputQueue_*`, `ALooper_*`, `AConfiguration_*`, `AAssetManager`), so it can be driven through `native_app_glue` rather than the full Java GLSurfaceView path. JNI surface = only **12 Java classes** (most trivial: Build/VERSION/SystemClock/Locale/HashMap; real work = UnityPlayer/UnitySendMessage, PlayerPrefs, ReflectionHelper, FMODAudioDevice ~5 audio methods). Audio: FMOD has audiotrack(JNI) + opensl backends — neither on webOS — bridge AudioTrack JNI → webOS PCM. Prime31 social/IAP managers (Facebook/Twitter/GameCircle/Amazon) → stub to no-ops.

Make-or-break unknown: bionic-loader ↔ Mono JIT (needs mmap PROT_EXEC; PDK apps get exec pages). Recommended first step = thin spike (dlopen both libs, reach ANativeActivity_onCreate with a black EGL window) before building the JNI shim. User can provide the ACL to reuse its bionic loader.

**2026-08-27 — native-Mono stage planned.** apk libmono = Mono **2.6.5**; upstream `Unity-Technologies/mono` branch `unity3.5` (2.6.5, corlib 82). libunity imports 118 `mono_*` (list in project `plan/tr2-mono-imports.txt`). Fast-TLS theory refuted (no `mrc p15` in libmono). Plan with checkpoints A–E: project `plan/TEMPLERUN2-MONO.md` — build glibc libmono with PalmPDK gcc 4.3.3 directly (no two-toolchain trick needed), host-lib bridge into apkenv hook table (hooks win over lib symbols at reloc), blacklist apk libmono.

**2026-08-27 EXECUTED — checkpoints A+B met, bridge code complete, device-blocked.**
- Native glibc Mono **builds**: `apkenv/hostlibs/webos/libmono-webos.so` via `apkenv/tools/build-mono-webos.sh` (clone→pin→patch→autoreconf→configure→make, validated from a clean clone). Max symbol version GLIBC_2.4.
- **Pin proven exact:** our glibc build's dynamic export set is *identical* to the apk's bionic `libmono.so` — 910 symbols, zero diff both directions.
- apkenv gained a **general host-library bridge**: `compat/hostlib.[ch]`, `APKENV_HOST_MONO=<path>`. `dlopen`s a glibc `.so` and registers its symbols as hooks, so bionic code binds to it (the linker checks hooks before library symbols). Reusable for any engine carrying its own runtime. Host libs go in `apkenv/hostlibs/`, never `apkenv/libs/` (that's the *bionic* sopath, and packaging copies `*.so` out of it).
- **Cross-build gotcha worth remembering generally:** old-glibc (2.5) headers + gcc 4.3 `-std=gnu99` + `-D_FORTIFY_SOURCE=2` ⇒ `multiple definition of realpath/fgets/gets/...`, because `bits/*.h` use bare `extern __always_inline`. Fix: **`-fgnu89-inline`**. Will bite any PalmPDK cross-build, not just Mono.
- **CHECKPOINTS C + D MET on device (2026-08-27).** C: `monotest` alone — `mono_jit_init_version` OK, JIT ran managed code, `Environment.Version=3.0.40818.0`, PASS. D: under apkenv — **121/121 symbols bridged**, libunity links, full Java host contract runs, and **Mono loads `mscorlib` into the Unity Root Domain**. The bionic-Mono SIGSEGV in `mono_jit_init_version` is GONE; that whole ABI-corruption class is closed.
- **Bridge set is 121, not 118**: derive it as {libunity UNDEFINED} ∩ {libmono DEFINED}. The `mono_` prefix misses `g_free` (eglib) + `GC_delete_thread`/`GC_lookup_thread` (Boehm), and libunity fails to link without them.
- **TITLE SCREEN RENDERS (2026-08-27).** Root cause of the crash: unity.c overrode `CallObjectMethod` but not **`CallObjectMethodV`**, so the va_list form hit jnienv.c's generic fallback which returns the `GLOBAL_J` sentinel for any unanswered object call → NULL from `GetStringUTFChars` → `strlen(NULL)`. **Rule: override the `V` variant of every `Call*Method` you override.**
- **The blank-screen bug was duplicate GLES hook names** — `gles_mapping.h`/`gles2_mapping.h` share **68** names; both tables got registered and `bsearch` picked arbitrarily, splitting the engine's calls across two wrappers against one context. `register_hooks_nodup()` fixed it. *Probing only one wrapper table gave me a confidently WRONG "0 draws" reading first — instrument every path a symbol can take.*
- Also needed: `nativeResize(w,h,w,h)` + `nativeResume()` **after** prepareGameLoop (order from `UnityPlayer.smali`), builtin-lib matching by **basename** (libunity dlopens `/system/lib/libEGL.so`), a real PlayerPrefs store (managed `SetX()` throws and kills `Awake()`), and a **software ETC1 decoder** (`compat/etc1.c`, unit-tested) since the Adreno 220's ES1 context rejects `GL_ETC1_RGB8_OES`.
- **ES2 is REQUIRED for this game and IS obtainable.** `settings.xml gles_mode=2`, manifest `uses-gl-es 0x20000`; all `TempleRun2/*` shaders are ES2-only (no fixed-function pass, no Fallback) → the "purple" 3D is Unity's **error shader**, not textures. SDL's own ES2 request fails (`EGL_BAD_ALLOC`, its attrib shape) but `webos://knowledge/nizovn-packages` records direct EGL+GLES2 *working* on the TouchPad. Plan: interpose `eglChooseConfig`/`eglCreateContext` in-process (apkenv links `-rdynamic -lEGL`), log first, then fix the config choice while SDL keeps owning the surface.
- **Packaged + launchable:** `com.apkenv.templerun2` v0.1.2, built with `packaging/build-ipk.sh` (new `HOSTLIBS=` ships the native Mono in `hostlibs/webos/`, `APKENV_HOST_MONO` via `android/apkenv.env`). 6600+ frames, no crashes.
- **Input focus comes from the LAUNCHER, not `novacom run`** (confirmed both ways: novacom = `ev_total=1`/no `SDL_ACTIVEEVENT`; icon = 26 BUTTONDOWN + 26 UP). Test touch only from a packaged `.ipk`.
- **`GetStringUTFChars` must return a COPY in every module** — the generic `ReleaseStringUTFChars` frees what Get returns, so returning `str->data` aborted on first touch with `double free or corruption`. Same trap already fixed in `jni/jnienv.c` for WMW2.
- **Orientation: the game IS portrait** (manifest `screenOrientation=1` on every Unity activity). The engine's `setOrientation(0)` was our own faked `getOrientation()=0` echoed back — never treat the engine's reaction to a faked answer as evidence. Needs an ES2 render-to-FBO present (768×1024) + rotated touch.
- **Touch: `nativeTouch(IFFIJI)`'s last int is the `MotionEvent` SOURCE** (`0x1002` = TOUCHSCREEN, hard-coded in `UnityPlayer.onTouchEvent`); `unity.c` passes 0. UI is NGUI (raycasts from `Input.touches`), so this alone should make the menu respond. Read the Java caller for *every* argument.
- **Current plan (2026-08-27): project `plan/TEMPLERUN2-RENDER-INPUT.md`** — Stage T touch source → Stage G ES2 context via EGL interposition (+ hook-table precedence must follow the real context version; ETC1 decode moves to the ES2 wrapper if the ES2 context lacks the extension; log shader compile errors) → Stage P portrait FBO on ES2.
- **Prior art worth reading first: `touchpad-porting.md` in https://github.com/webOSArchive/Pre-PDK-to-TouchPad-Ports** — same class of Adreno bugs (e.g. `glClear(GL_DEPTH_BUFFER_BIT)` is a no-op while `glDepthMask` is FALSE → garbled render), a symptom→cause table, and the same lesson: instrument on-device early (DRIVER took ~11 blind attempts before a 10-line trace).
- **novacom gotchas:** a hung `novacom run` wedges the HOST daemon (`novacom -l` then times out forever) — recover with `sudo systemctl restart novacomd`. `novacom run`'s cwd is `/`, which webOS mounts **ro** (`/var` and `/media/internal` are rw). Always run device commands under `timeout`.
- **2026-08-27 session 2 — TOUCH WORKS, ES2 CONTEXT WORKS, renderer choice still wrong.** Package 0.1.13; plan/execution log: project `plan/TEMPLERUN2-RENDER-INPUT.md`.
  - **Touch: `nativeTouch`'s trailing int is the MotionEvent SOURCE (`0x1002`), not spare.** We passed 0. With that + a monotonic `eventTime`, the menu responds. General rule: read the Java caller for EVERY argument of a native method, not just their order.
  - **ES2 CAN be created on the TouchPad — the "never retry ES2" note was wrong.** Root cause of `EGL_BAD_ALLOC`: **the first EGL context in the process must be ES1**; after one ES1 context exists (even destroyed), ES2 succeeds on all 27 configs. `apkenv_egl_warmup()` in `apkenv/platform/webos_egl_shim.c` does that before SDL asks — always on. Reusable for any ES2 engine on webOS.
  - **In-process EGL interposition is the way to debug Palm's SDL:** apkenv links `-rdynamic -lEGL`, so `eglChooseConfig`/`eglCreateContext` defined in the executable intercept libSDL's own calls. It disproved both planned config fixes in one run (SDL was already being handed an ES2-capable config).
  - **`APKENV_GL_SNAPSHOT=<frame>` → `glReadPixels` → PPM on /media/internal** (`platform/webos.c`). There is no screenshot tool for a GL app on webOS 3.0.5 and /dev/fb0 lacks the accelerated layer, so this is how to SEE the render. (webOS's built-in screenshot writes to `/media/internal/screencaptures` — worth trying for non-GL.)
  - **`palm-launch` on a RUNNING app only refocuses it** — the old process keeps writing the log, so you analyse the previous build's output while md5sum says the new binary is installed. `killall` over novacom often reports "unexpected EOF from server" and does not take; `pidof` + `kill -9` does. Encoded in `apkenv/tools/tr2-run.sh` (kill→install→launch→pull).
  - **(SOLVED, see below) Unity built its fixed-function ES1 device under an ES2 context** (measured: `glMatrixMode`/`glTexEnvf`/`glEnableClientState`, `glCreateShader` never called), so the 8 ES2-only shaders draw magenta. Ruled out by measurement: config/driver/jail/PDL/SDL; `GL_VERSION` (now correctly reports "OpenGL ES 2.0" via libGLESv2 and Unity still picks ES1); entry-point probing (libunity calls `eglGetProcAddress` exactly twice, for NV timers — it binds GL via DT_NEEDED); the missing `nativeRecreateGfxState` (now called, no change); Java `gles_mode` (never reaches native). Next: disassemble libunity's branch around "Creating OpenGLES1.x/2.0 graphics device" with **capstone** (the lib is PIC, so naive 4-byte xref scans find nothing).
  - **Correction to a previous entry: the Adreno 220 DOES advertise `GL_OES_compressed_ETC1_RGB8_texture`** on both ES1 and ES2 (full extension strings in `plan/logs/tr2-es2-7.log`). The CPU ETC1 decoder was written on a false premise — the texture rejections were most likely the duplicate-GLES-hook bug.
- **2026-08-27 — TEMPLE RUN 2 RENDERS AND PLAYS** (`com.apkenv.templerun2` 1.0.0). Menu responds to taps; a run renders complete 3D (track, sky, HUD). Two final bugs, both found by instrumenting:
  1. **Unity chose its fixed-function ES1 device under an ES2 context.** The selector is ONE global byte tested at `libunity+0x2d2f74`: 0 → ES1 device init (`+0x2b69b4`), non-zero → ES2 (`+0x2c44ac`). `modules/unity.c` sets the flag and rewrites `bne`→`b`, verifying the expected instruction words first. **Method:** the "Creating OpenGLES1.x/2.0 graphics device" strings in libunity have **no code references at all** (dead strings in a release build) — grep finds nothing. What worked: one-shot markers in BOTH wrapper tables proved the fixed-function path, then a **stack scan** at the first `glGetString` (glibc can't unwind bionic frames; scan for stack words pointing into the lib preceded by a BL/BLX — apkenv's crash-handler trick) gave the caller chain, and one frame's disassembly held the branch.
  2. **The ES2 device then drew through `libGLES_CM`** → a flat clear colour, no geometry. The ~68 shared GLES1/GLES2 entry points are separate driver front-ends with separate state. Choosing the right wrapper at resolution time is impossible: `[HOOKRES]` tracing showed **the engine's GOT is bound while the apk's libs load, before any context exists**. Fix: keep the wrappers, re-point the *driver* pointers they call through once the context exists (`apkenv_gles1_bind_driver` in `compat/gles_wrappers.c`).
- **General traps worth keeping:** `__builtin_return_address(0)` must be taken IN the wrapper, not in a helper it calls (it silently "works" only where the helper gets inlined). And an ES2 context on the TouchPad is refused **only when it is the first context in the process** — prime with one ES1 context (`apkenv_egl_warmup()`), which is why raw EGL tests always seemed to work.
- **Reusable tools:** `APKENV_GL_SNAPSHOT=<frame>` (glReadPixels→PPM, the only way to see a GL app's screen on webOS 3.0.5), `APKENV_UNITY_AUTOTAP=<frame>:<x>:<y>` (scripted taps through the real input path — verify gameplay with nobody at the device), `apkenv/tools/tr2-run.sh` (kill→install→launch→pull, one command), `tools/egl2test.c`.
- **2026-08-27 — FULLY PLAYABLE (`com.apkenv.templerun2` 1.0.4): menu, touch, textured 3D, and TILT STEERING.** Landscape is final — the user confirmed the game adapts and looks right, so the portrait/FBO work is **cancelled**, not deferred.
- **apkenv's accelerometer never worked on webOS at all** — `platform/common/sdl_accelerometer_impl.h` uses `SDL_JoystickOpen(0)` and **webOS 3.0.5 has no joydev** (sensors/controllers are evdev-only, `webos://knowledge/game-controllers`), so it silently reported a dead-still device for every module. Fixed generally: `platform/common/pdl_accelerometer_impl.h` implements apkenv's `struct Accelerometer` over PDL (`PDL_SensorExists`/`PDL_EnableSensor`/`PDL_PollSensor`), SDL kept as fallback. **PDL reports g, not m/s²** (measured `|g|=1.065`) — scale by 9.80665 for apkenv's Android-frame contract, and drain the poll queue to the newest sample or tilt lags.
- **Unity has no native polling path for acceleration:** it arrives only via `UnityPlayer.nativeSensor(x,y,z,tsNanos)` (`p.onSensorChanged` type 1 → `p$1.run()`), so `Input.acceleration` stays (0,0,0) unless the host calls it every frame. The remap is the host's own table with `K = -1/9.80665` (m/s² → g, negated).
- **The tilt frame was a quarter-turn off, and the giveaway was the RESTING value, not the swing.** The roll signal was reaching `Input.acceleration.x` with the correct sign, but the game (portrait-built, presented landscape) reads a different axis — which carried a constant −0.86 (gravity) → constant drift, whose direction flipped between sessions because that axis was `+raw.x`, the pitch axis. Answer: `row=0, invy=1` (roll onto Y, gravity parked on X). **When a tilt game drifts, look at what the resting frame puts on each axis, not just at which axis moves.**
- **Calibration loop worth reusing:** the app dir is read-only and the env file ships inside the package, so `modules/unity.c` also reads `/media/internal/apkenv-tilt.conf` (`row`/`invx`/`invy`) — a mapping change is one `novacom put` + relaunch instead of a repackage+install. `row` picks among the four orientation rows the real Java host supports, so every setting stays a legitimate configuration.

- **2026-08-27 — RELEASED `com.apkenv.templerun2` 1.3.0** (portrait, touch, swipe, tilt, textured 3D, SFX; **no music, no splash**). Full trail: project `plan/TEMPLERUN2-RENDER-INPUT.md`; general lessons now in `PORTING-PLAYBOOK.md`.
- **THE lesson: `UnityPlayer.nativeInit(II)` is `(glesMode, splashMode)`, NOT `(width, height)`** (read from `UnityPlayer$24`). We passed the screen size for the entire port, so the engine saw glesMode=1024 → built its **fixed-function renderer** (every ES2-only shader drew as magenta error material) and splashMode=768 → **no splash**. The size always arrived via `nativeResize`. Fixing it makes the engine set its own device flag — the binary patch of `libunity+0x2d2f78` became dead code. **A patch that works proves you found the mechanism, not the cause.**
- **Two of my own confident conclusions were WRONG, both from probes that measured the wrong thing:** (a) "FMOD never creates a stream thread" — `/proc/self/task` shows `FMOD stream thr` and `asyncProcessor`; apkenv's `pthread_create` log only sees threads created through its own hook. (b) "the music data is read once" — a seek probe cannot see sequential reads; byte accounting shows exactly one 64 KB stream buffer primed and never consumed. **Count from /proc, not from your own instrumentation; and always run a positive control (`MONO_VERBOSE_METHOD=Awake` before trusting `=StartMainMenuMusic`).**
- **Music, precisely where it stands:** ruled out — our pump (meter: SFX peak vs music silence), file IO, volume/prefs, the game logic (`StartGameMusic` runs and does Stop/clip/Play), `fmodInitJni` (real gap, closed), missing threads. Remaining: the stream is primed and its channel never consumes. Splash is in the same neighbourhood — `splash.png` IS read but 0 draw calls happen around `unityAndroidInit`.
- **Process lesson the user had to point out:** after portrait/tilt landed, many device cycles produced no user-visible change. When runs stop changing what the user can see or hear, stop and report instead of deploying again.

- **2026-08-27 — SHIPPED `com.apkenv.templerun2` 1.4.0: music AND splash both solved, port complete.**
  Portrait, touch/swipe/tilt, textured 3D, SFX, music, boot splash. Both were solved by asking *whose
  job is this?* rather than by more engine archaeology — see [[shim-owns-the-host-platforms-jobs]].
  - **Music:** the native FMOD stream is still stuck (primed 64 KB, channel never consumes) and must
    be left alone — inline-hooking libunity's FMOD internals crashed the device. Shipped instead: a
    PCM bed mixed into the working AudioTrack pump (`APKENV_FMOD_MUSIC_PCM`). It **follows the game's
    own music slider**, because a Unity game stores that in PlayerPrefs and *apkenv implements
    PlayerPrefs* — `novacom get` on the device's `playerprefs.txt` named the key (`TR Music Volume`)
    in one step. `APKENV_FMOD_MUSIC_PREF`.
  - **CORRECTION to the entry above — "`splash.png` IS read" was WRONG.** The engine never opens it.
    `lib/armeabi-v7a/libunity.so` is a 43 KB **proxy**; the real 6.8 MB engine in `assets/libs/`
    contains no `splash` string but its own `UnitySplash*.png` watermarks, and the Java host has only
    the `splash_mode` settings key. The "is read" came from a seek-range probe over the apk that
    cannot tell an open from a read crossing that offset range. See
    [[static-answer-before-dynamic-probe]].
  - **Splash:** drawn by the host. `APKENV_SPLASH_RGB` uploads a raw RGB24 image and rides the
    existing rotated present quad; retires on the engine's first draw (`apkenv_gl_draws`), so there
    is no timer to tune. The load is one blocking `unityAndroidInit` during which nothing presents,
    so two `platform->update()` calls before it hold the image for the whole load.
  - **The music asset, exactly:** `assets/bin/Data/sharedassets0.assets.resS` (1277793 bytes, STORED
    in the apk at `0x1cfd7f8..0x1e35759`) is **TWO CONCATENATED 44.1 kHz stereo MP3s with no
    container** — Unity keeps only the offsets, in `sharedassets0.assets`. **Split at `0xe4800`:**
    track 1 = 935936 bytes / 60.08 s (the in-game music, the one shipped), track 2 = 341857 bytes /
    23.47 s. Decode track 1 to **24000 Hz stereo S16** (FMOD's *measured* output rate — the pump
    does no resampling) → 5765328 bytes, md5 `988d1789aedd4b84c01b83670eafa959`. Decoding the
    `.resS` whole silently concatenates both tracks; the split is the non-obvious step and the whole
    reason `tools/tr2-extract-music.sh` exists.
  - **The splash asset:** `assets/bin/Data/splash.png`, 640x1136 RGB (an iPhone-5-shaped launch
    image) → cover-cropped to the 768x1024 portrait FBO size, raw RGB24, **bottom row first** (GL's
    texture origin is bottom-left; ffmpeg writes top-down, so `vflip`).
  - Package-time asset extraction (no image/audio decoder is linked): `tools/tr2-extract-music.sh`,
    `tools/tr2-extract-splash.sh`, shipped via `build-ipk.sh`'s new `EXTRAS=`. Both md5/size-check
    their output — the decoded files are gitignored game content and live only in
    `packaging/extras/`, never in `packaging/stage/` (wiped by every build).
